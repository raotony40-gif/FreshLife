# 乐鲜生活 PRD

## 1. 目标

### 1.1 项目名称

乐鲜生活

### 1.2 产品定位

乐鲜生活是面向社区用户的生鲜电商平台，提供水果、蔬菜、肉禽蛋奶、粮油调味、日配冷藏等商品的线上购买和本地配送服务。

项目第一阶段目标不是追求功能完整，而是尽快上线可运营版本，验证社区用户是否愿意持续下单。

### 1.3 目标用户

- 社区居民：希望快速购买日常生鲜商品。
- 商家或门店运营人员：负责商品、库存、订单处理。
- 配送员：负责接单、配送、完成订单。
- 平台管理员：负责用户、商品、订单和基础运营管理。

### 1.4 核心业务流程

用户下单 -> 商家接单 -> 配送员配送 -> 用户签收

### 1.5 MVP 成功标准

- 用户可以完成从注册登录到支付下单的完整流程。
- 商家可以管理商品、库存并处理订单。
- 配送员可以接单、更新配送状态并完成订单。
- 管理员可以查看用户、商品和订单数据。
- 平台可以支撑小范围社区试运营。

### 1.6 暂不开发范围

以下功能不进入第一阶段：

- 会员体系
- 优惠券
- 拼团
- 秒杀
- 直播带货
- 积分商城
- 多商户复杂结算
- 智能推荐
- 复杂数据大屏
- 微服务架构
- Kubernetes、Kafka、Elasticsearch、RabbitMQ

以上功能统一进入后续待办列表，等真实订单数据验证后再决定是否开发。

## 2. 功能说明

### 2.1 用户端

#### 2.1.1 注册登录

目标：降低用户进入门槛，保证后续订单可追踪。

功能：

- 手机号注册
- 手机号验证码登录
- 用户基础信息维护
- 默认收货地址维护

第一阶段可先使用测试验证码或短信服务商验证码。正式上线前接入真实短信服务。

#### 2.1.2 商品浏览

目标：提升用户找商品和下单效率。

功能：

- 首页展示商品分类
- 展示推荐商品
- 展示商品列表
- 商品详情页展示图片、价格、库存、规格、描述
- 商品售罄时禁止加入购物车

#### 2.1.3 商品搜索

目标：帮助用户快速找到明确想买的商品。

功能：

- 按商品名称搜索
- 按商品标签搜索
- 搜索结果按上架状态和库存过滤

第一阶段使用 MySQL LIKE 查询即可，不引入 Elasticsearch。

#### 2.1.4 购物车

目标：支持用户批量购买，提高客单价。

功能：

- 加入购物车
- 修改购买数量
- 删除购物车商品
- 展示购物车总价
- 下单前校验库存和商品状态

#### 2.1.5 下单

目标：完成交易闭环。

功能：

- 从购物车创建订单
- 选择收货地址
- 展示商品金额、配送费、订单总额
- 提交订单时锁定库存或扣减库存
- 生成订单编号

第一阶段建议采用下单即扣库存，支付超时后释放库存，逻辑简单、风险可控。

#### 2.1.6 支付

目标：支持订单实际成交。

功能：

- 创建支付单
- 支付成功后订单进入待接单状态
- 支付失败或超时订单关闭

第一阶段可先预留微信支付接口；开发联调阶段支持模拟支付，方便快速跑通流程。

#### 2.1.7 订单查询

目标：降低用户咨询成本，提升履约透明度。

功能：

- 查看订单列表
- 查看订单详情
- 查看订单状态
- 确认收货

订单状态：

- 待支付
- 待接单
- 待配送
- 配送中
- 已完成
- 已取消
- 已退款

### 2.2 商家端

#### 2.2.1 商品管理

目标：保证平台有可售商品。

功能：

- 新增商品
- 编辑商品
- 上架商品
- 下架商品
- 上传商品图片
- 设置商品分类、价格、规格、库存

AI 可接入点：

- 根据商品名称自动生成商品标题
- 根据商品信息生成商品描述
- 自动生成商品标签

#### 2.2.2 库存管理

目标：减少超卖和履约失败。

功能：

- 查看库存
- 修改库存
- 库存为 0 自动标记售罄
- 下单扣减库存
- 订单取消释放库存

#### 2.2.3 订单管理

目标：让商家快速处理订单，提高配送效率。

功能：

- 查看待接单订单
- 接单
- 拒单
- 查看订单商品明细
- 将订单标记为待配送

第一阶段拒单需要填写原因，便于后续分析缺货和履约问题。

### 2.3 配送端

#### 2.3.1 接单

目标：让配送员获取可配送订单。

功能：

- 查看待配送订单
- 接单
- 查看收货地址和联系人

#### 2.3.2 配送

目标：跟踪配送进度。

功能：

- 开始配送
- 更新订单为配送中
- 联系用户

#### 2.3.3 完成订单

目标：完成履约闭环。

功能：

- 标记已送达
- 用户确认收货
- 超过一定时间可由系统自动完成

### 2.4 管理后台

#### 2.4.1 用户管理

目标：支撑基础运营和售后处理。

功能：

- 用户列表
- 查看用户详情
- 禁用异常用户

#### 2.4.2 商品管理

目标：平台统一监管商品质量。

功能：

- 商品列表
- 查看商品详情
- 上架和下架商品
- 查看库存

#### 2.4.3 订单管理

目标：支持客服和运营快速定位问题。

功能：

- 订单列表
- 按状态筛选
- 查看订单详情
- 手动取消异常订单
- 查看配送信息

### 2.5 AI 功能规划

第一阶段只做低成本、能提升效率的 AI 能力，不影响主流程上线。

优先级：

1. 商品文案生成：提升商品录入效率。
2. 运营文案生成：生成社群促销文案。
3. AI 客服知识库：回答配送时间、售后规则、商品问题。
4. 数据分析建议：根据订单数据输出热销、滞销、复购建议。

第一阶段 AI 功能可放在管理后台中，不影响用户下单主链路。

## 5. 开发步骤

### 5.1 第一阶段：跑通交易闭环

目标：完成最小可运营版本。

步骤：

1. 初始化 Node.js 单体后端项目。
2. 设计 MySQL 数据库表。
3. 开发用户注册登录。
4. 开发商品分类、商品列表、商品详情。
5. 开发购物车。
6. 开发创建订单。
7. 开发模拟支付。
8. 开发商家接单。
9. 开发配送员接单和完成配送。
10. 开发订单查询。

验收标准：

- 一个用户能完整完成下单。
- 商家能看到订单并接单。
- 配送员能接单并完成配送。
- 用户能看到订单状态变化。

### 5.2 第二阶段：上线运营后台

目标：让运营人员可以维护平台基础数据。

步骤：

1. 开发管理后台登录。
2. 开发用户管理。
3. 开发商品管理。
4. 开发库存管理。
5. 开发订单管理。
6. 接入 OSS 上传商品图片。
7. 接入正式短信服务。

验收标准：

- 运营人员不需要改数据库即可管理商品和订单。
- 商品图片可正常上传和展示。
- 用户可使用真实验证码登录。

### 5.3 第三阶段：接入正式支付和试运营

目标：开始小范围真实交易。

步骤：

1. 接入微信支付。
2. 处理支付回调。
3. 增加支付超时关闭订单。
4. 增加订单异常日志。
5. 配置服务器、域名、HTTPS。
6. 小范围社区试运营。

验收标准：

- 用户可以真实支付。
- 支付成功后订单状态准确更新。
- 支付失败、取消、超时场景可处理。
- 平台能支持小范围真实订单。

### 5.4 第四阶段：AI 提效功能

目标：提升商品录入和运营效率。

步骤：

1. 管理后台增加 AI 商品文案生成入口。
2. 管理后台增加 AI 社群文案生成入口。
3. 根据订单数据生成热销和滞销商品报表。
4. 输出简单运营建议。

验收标准：

- 商品录入时间减少。
- 运营可以快速生成微信群推广文案。
- 能看到基础销售分析。

## 6. 风险分析

### 6.1 库存超卖风险

风险：多个用户同时下单可能导致库存不足。

方案：

- 下单时使用数据库事务扣减库存。
- 扣减条件必须包含 `stock >= quantity`。
- 支付超时或订单取消时释放库存。

### 6.2 配送履约风险

风险：配送员不足会导致订单延迟。

方案：

- 第一阶段只服务有限社区范围。
- 后台展示待配送订单。
- 超时未接单订单由运营人工处理。

### 6.3 商品质量和售后风险

风险：生鲜商品容易出现损耗、变质和售后纠纷。

方案：

- 商品详情明确规格和单位。
- 订单保留下单时商品价格和名称。
- 后台支持查看订单明细。
- 售后退款功能进入第二阶段，不影响 MVP 主流程。

### 6.4 支付接入风险

风险：微信支付申请和联调耗时较长。

方案：

- 开发阶段使用模拟支付。
- 支付模块保留统一支付单接口。
- 正式上线前再接入微信支付。

### 6.5 成本风险

风险：过早引入复杂架构导致开发和运维成本上升。

方案：

- 后端采用 Node.js 单体架构。
- 数据库使用 MySQL。
- 搜索使用 MySQL LIKE。
- 缓存只在必要时使用 Redis。
- 图片使用 OSS，避免服务器磁盘存储膨胀。

- 日志可查看。
- 数据库已配置备份。
- 域名和 HTTPS 配置完成。

### 7.4 小范围试运营

建议先选择 1 个社区试运营，控制商品数量和配送范围。

试运营重点观察：

- 下单转化率
- 复购率
- 客单价
- 配送时长
- 缺货率
- 退款和投诉原因

### 7.5 运营指标

| 指标 | 说明 | 第一阶段目标 |
| --- | --- | --- |
| 日订单数 | 每日订单数量 | 20 单以上 |
| 复购率 | 用户重复购买比例 | 20% 以上 |
| 平均配送时长 | 从接单到送达时间 | 60 分钟内 |
| 缺货率 | 因库存不足导致异常订单比例 | 5% 以下 |
| 客单价 | 单个订单平均实付金额 | 30 元以上 |

## 8. 后续优化

后续功能必须基于真实运营数据决定。

优先考虑：

- 售后退款
- 优惠券
- 配送费规则
- 商品销量排行
- 商品复购提醒
- AI 客服
- AI 运营分析
- 多社区配送范围管理

暂不考虑：

- 微服务
- 复杂推荐系统
- 大数据平台
- 独立骑手 App 的复杂调度算法

## 9. 决策记录

### 9.1 为什么第一阶段使用单体架构

单体架构开发最快、部署最简单、运维成本最低，适合项目早期验证商业模式。

### 9.2 为什么第一阶段不做复杂营销

项目当前最重要的是验证用户是否愿意购买，以及订单履约是否能跑通。复杂营销会增加开发成本，也会干扰真实需求验证。

### 9.3 为什么搜索先用 MySQL

MVP 阶段商品数量有限，MySQL 查询足够支撑。等商品数量和搜索需求增长后，再评估是否引入专业搜索服务。
